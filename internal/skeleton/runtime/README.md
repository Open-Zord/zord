# Your Zord service

This project was generated by [`zord new`](https://github.com/Open-Zord/zord). It
is a standalone Go service built on **hexagonal architecture** (ports & adapters)
with an HTTP entrypoint, MySQL persistence and a type-safe dependency registry.

You own all of this code — edit it freely. The `zord` CLI stays external and
maintains the project for you (code generation, the architecture gate, migrations).
Install it once:

```sh
go install github.com/Open-Zord/zord/cmd/zord@latest
```

---

## Run it

### Everything in Docker (recommended)

```sh
docker compose up -d        # MySQL + the app (hot-reload via air)
zord migrate                # create the tables from schemas/schema.my.hcl
curl localhost:9000/v1/health   # -> "OK"
```

The app listens on `HTTP_PORT` (default `9000`) under the `API_PREFIX` (default
`v1`), so the health check is `GET /v1/health`.

### Locally against a containerized MySQL

```sh
docker compose up -d zord-mysql     # just the database (exposed on host :3307)
zord migrate
go run ./cmd/http
```

`.env.http` carries committed **dev defaults** (local MySQL on `127.0.0.1:3307`).
In Docker, the `zord-http` service overrides `DB_URL`/`DB_PORT` to reach MySQL over
the internal network. For real credentials create a `.env` at the root — it wins
and is gitignored. In production the binary reads only system env vars.

> The project ships with an example `dummy` domain. `POST /v1/dummy` returns 500
> until you've run `zord migrate` (the table doesn't exist yet). The other dummy
> CRUD handlers are scaffold stubs for you to complete.

## Architecture

Dependencies always point inward: transport and persistence adapters depend on the
application core, never the reverse. The architecture gate enforces this (see below).

```
cmd/http/                HTTP entrypoint: main, server, routes, handlers, middlewares
internal/
  application/
    domain/              domain structs + their Repository interfaces (ports)
    services/            use cases, one folder per operation (create/get/list/…)
    providers/           shared ports/primitives (baserepo, baseservice, pagination)
  repositories/          sqlx adapters implementing the domain Repository ports
pkg/                     transport-agnostic primitives (see below)
bootstrap/http/          the single dependency-injection wiring point
schemas/schema.my.hcl    Atlas HCL schema (source of truth for migrations)
```

### Layers

- **`internal/application/domain/<name>/`** — the domain struct and the
  `Repository` interface it needs. Pure; no framework or SQL.
- **`internal/application/services/<domain>/<usecase>/`** — one use case per
  folder (`service.go` + `request.go`/`response.go`). Orchestrates domain and
  ports; this is the only layer allowed to orchestrate.
- **`internal/repositories/<domain>/`** — the sqlx adapter that implements the
  domain's `Repository` port.
- **`cmd/http/`** — Echo server, route declarations and 1:1 HTTP handlers per use
  case.
- **`pkg/`** — reusable primitives, importable anywhere: `apperror` (error model),
  `config`, `database` (sqlx/MySQL), `idcreator` (ULID), `logger` (zerolog),
  `registry` (the DI container) and `validator`.

### Dependency injection (`bootstrap/`)

`bootstrap/` is the **single authorized place** where dependencies are constructed
— `cmd`, `internal` and `pkg` never wire themselves. `http.Setup()` (in
`bootstrap/http`) loads config and assembles the graph into `pkg/registry` in
topological order:

```
pkg → repositories → services → handlers
```

Each layer has its own `register*` file (`bootstrap/http/pkg.go`,
`repositories.go`, `services.go`, `handlers.go`). Dependencies are resolved with
the typed helper `registry.Resolve[T](reg, key)`. The scaffold `register` /
`unregister` subcommands edit these files for you — you rarely touch them by hand.

## Generate code (scaffold)

Code generation is **AST-pure**: `zord scaffold` edits the Go AST of the target
layer, so output stays compilable and idempotent — it never templates whole files
blindly. One command group per architectural layer:

| Group | Subcommands | Purpose |
|---|---|---|
| `domain` | `create`, `delete` | Domain struct under `internal/application/domain/<name>/` |
| `field` | `add`, `remove` | Granular fields on a domain struct |
| `derive` | `schema` | (Re)generate or remove the domain's Atlas HCL block |
| `repository` | `create`, `delete`, `port`, `unport`, `register`, `unregister` | sqlx adapter + Repository port + DI wiring in `bootstrap/http/repositories.go` |
| `service` | `create`, `delete`, `register`, `unregister` | Use-case-per-folder service + DI wiring in `bootstrap/http/services.go` |
| `request` | `field`, `validator` | `request.go` fields and validation toggle of a use case |
| `response` | `field` | `response.go` fields of a use case |
| `handler` | `create`, `delete`, `register`, `unregister` | 1:1 HTTP handler + DI wiring in `bootstrap/http/handlers.go` |
| `route` | `create`, `add`, `remove`, `delete`, `register`, `unregister` | Route file per domain + registration in `cmd/http/routes/declarable.go` |
| `projection` | `create`, `field` | Projection structs (return types for aggregate queries) |

```sh
zord scaffold --help
zord scaffold <group> --help
zord scaffold <group> <subcommand> --help
```

> When generating inside a Docker container, fix file ownership afterwards with
> `sudo chown $USER:$USER -R .`.

## The architecture gate

```sh
zord arch-analyse
```

Runs ~19 validations over the project in the current directory (allowed imports,
layer dependencies, no cyclic imports, context propagation, provider purity, no
mutable package globals, naming/placement, `pkg/` never importing `internal/`, …).
It is the contract that keeps the hexagonal boundaries intact — generated or
hand-written, **code is only accepted when the gate passes**. Run it before every
commit.

## Migrations

The schema lives in `schemas/schema.my.hcl` (Atlas HCL). `zord derive schema <Domain>`
regenerates a domain's block from its struct; then apply it:

```sh
zord inspect        # show the current database vs. the HCL
zord migrate        # apply the HCL schema to the database
```
